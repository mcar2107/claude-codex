## Запрос и принятые решения

Пользователь хочет распространять наше решение запуска Claude Code через Codex
OAuth среди других пользователей. После обсуждения Go/Rust принято решение:
**оставляем JavaScript и Bun, не переписываем на Go/Rust**.

и самостоятельные бинарники со встроенным Bun. Предпочтительное направление —
общая кодовая база, пригодная для npm и standalone-сборок. Возможность собрать
весь текущий CCR в самостоятельный бинарник ещё не проверялась: не обещать, что
одной команды `bun build --compile` достаточно.

Рабочий каталог: `/Users/corvus278/Projects/claude-codex`.
Пользователь выбрал имя проекта `claude-codex`; каталог и package metadata
уже переименованы. npm scope, публичный CLI, GitHub-репозиторий и собственная
лицензия пока не определены; занятость имени в registry не проверена. Эти вопросы не мешают локальной
подготовке пакета. В этой сессии пользователь попросил только сохранить
инструкцию; упаковку ещё предстоит выполнить в следующей сессии.

## Что представляет собой текущее решение

Это наша обвязка поверх стороннего транспорта:

- пакет `@caeliq/claude-code-router`, установленная версия `2.1.16`;
- upstream: https://github.com/oakimov/claude-code-router;
- лицензия upstream — MIT, при включении его кода сохранять уведомления;
- для установленного CCR требуется Bun >= 1.4.0;
- на машине в предыдущей сессии были Node 24.21.0 и Bun 1.4.4;
- старый bridge: `zachristmas/claude-code-router-codex-oauth`;
- отдельный глобальный `ccr` от `@musistudio/claude-code-router` был версии 3.1.3
  и имел другой интерфейс. Не подменять им наш локальный CCR.

Схема:

```text
launcher
  → установленный Claude Code CLI
  → отдельный локальный CCR для этой сессии
  → transformer настроек модели/reasoning
  → Anthropic Messages → OpenAI Responses / Responses Lite
  → Codex backend с OAuth пользователя
  → обратное преобразование ответа
```

Claude Code выполняет инструменты и отвечает за интерфейс, MCP, CLAUDE.md,
разрешения и историю. Наш пакет не должен включать или переустанавливать сам
Claude Code. Он остаётся внешней зависимостью.

| --- | --- |
| `bridge.cjs` | CLI dispatch, запуск CCR и Claude, OAuth helper, doctor, сессионные overrides |

| `install.cjs` | заменяет глобальные команды и slash commands, сохраняет данные для отката |
| `verify.cjs` | проверки настроек, overrides, будущих model IDs, сохранности tools/messages и отката |

| `try-sol.cjs` | первоначальный эксперимент для Sol, не финальная точка входа пакета |

| `.runtime/` | приватные credentials, настройки, CCR bundle, временные файлы и backups |

`package.json` пока содержит только dependency с диапазоном `^2.1.16`.
README называет версию закреплённой, но это неточно: для воспроизводимого
выпуска нужно согласовать package.json и lockfile с реально проверенной версией.

## Поведение, которое нужно сохранить

- По умолчанию: `gpt-6.1-sol`, effort `xhigh`.
- Настройки применяются со следующего запроса, включая открытые сессии.
- Явные `--model` / `--effort` и переменные `CLAUDE_GPT_MODEL` /
  `CLAUDE_GPT_EFFORT` переопределяют сохранённые значения на время сессии.
- Несколько сессий имеют собственные процессы CCR, порты, PID и health metadata.
- OAuth-файл общий для сессий; CCR координирует refresh блокировкой файла.
- Есть login/status, doctor с реальным запросом, список и discovery моделей.
- Будущие `gpt-*` ID можно задать без редактирования allowlist.
- Кандидаты в конфигурации не равны моделям, доступным аккаунту. Проверять через
  discovery и реальные запросы, не обещать доступ по наличию имени в API docs.
- Для GPT-6/5.6 в текущем Codex transport разрешены low/medium/high/xhigh/max.
  none/minimal отклоняются, поскольку эта версия CCR иначе поднимает их до low.
  Не расширять уровни по документации обычного API без проверки OAuth transport.
- Обычный `claude` не должен менять маршрут или глобальные настройки.

Текущие команды: `claude-gpt`, `claude-gpt-settings`, `claude-gpt-auth`,
`claude-gpt-doctor`; slash commands — `/gpt-settings`, `/gpt-model`, `/gpt-effort`.
Для публичного пакета предпочтителен единый CLI с подкомандами, например:

```sh
claude-codex
claude-codex auth login
claude-codex auth status
claude-codex doctor
claude-codex settings set --model gpt-6.1-sol --effort xhigh
claude-codex models refresh
```

Это предложенный interface, а не уже установленный набор команд. Сохранение
старых aliases можно сделать опцией миграции без перехвата чужих команд.

## Главные проблемы перед выпуском

1. **State внутри проекта.** `.runtime` нельзя оставлять местом постоянного
   хранения пользовательских данных. Выделить настраиваемый user state/config
   directory, например `~/.claude-codex/`. Обновление npm-пакета не должно
   удалять токены или настройки. Не зашивать путь пользователя в файлы пакета.

2. **Правка минифицированного bundle.** `prepare.cjs` заменяет homedir paths
   регулярными выражениями. `bridge.cjs:sessionBundle` зависит от формы
   сгенерированных констант. `verify-transport.cjs` подменяет вызов `sje()` и
   обращается к внутреннему символу `sY.getServer`. Всё это зависит от конкретной
   сборки CCR. Предпочтительно добавить в исходники CCR настраиваемые state/config
   paths и поддерживаемую программную точку запуска. Рассмотреть upstream patch
   или небольшой отслеживаемый fork с минимальными изменениями. Не выдавать
   существующие regex-патчи за устойчивый interface.

3. **Node и внешний Bun.** Сейчас команды явно запускают `node` и `bun`, а
   установщик сохраняет абсолютный `process.execPath`. Для npm это нужно
   оформить штатными `bin` entrypoints; для standalone — включить транспорт
   и runtime в сборку. Дочерний сервер может запускаться тем же бинарником с
   internal subcommand либо работать внутри процесса. Внешние `bun cli.js`,
   динамический require плагина и загрузку WASM/assets надо адаптировать.

4. **Чистая авторизация.** `prepare.cjs` предполагает наличие OAuth-файла старого
   bridge. Новый пользователь должен входить с нуля. Импорт старой авторизации
   сделать явной миграцией, не обязательным условием запуска. Токены не печатать.

5. **Установщик.** Нынешняя ручная замена файлов в npm bin — локальная миграция,
   а не стандартная установка нового продукта. Не писать в пользовательский
   home из npm postinstall. Настройку slash commands оформить явным setup.

6. **Модели и labels.** Launcher пока использует `codex,gpt-6.1-sol` как alias,
   а transformer меняет фактическую upstream модель. Надпись Claude может
   отличаться от выбранной модели. Для публичной версии это надо объяснить или
   улучшить, не выдавая стартовую надпись за проверку фактического маршрута.

## Рекомендуемый порядок работы

1. Прочитать реальные файлы и локальные инструкции. Проверить текущую установку,
   не предполагая, что состояние глобальных команд осталось прежним.
2. Сохранить рабочую версию и приватные данные; изменения упаковки делать так,
   чтобы текущий запуск пользователя продолжал работать.
3. Выделить CLI, session lifecycle, settings/state, OAuth и CCR adapter в модули.
   Не строить универсальный многопровайдерный framework: нужен Claude → Codex.
4. Решить поддерживаемый способ интеграции с CCR и убрать патчи минифицированного
   кода из основного пути. Сохранить Bun.
5. Подготовить полноценный package.json: metadata, engines, bin, files allowlist,
   scripts, закреплённые зависимости, LICENSE и THIRD_PARTY_NOTICES.
6. Получить устанавливаемый `.tgz` через `npm pack`, проверить архив и чистую
   установку. Это первый проверяемый результат, ещё без публикации в registry.
7. Проверить standalone-сборку Bun на узком вертикальном сценарии: запуск,
   локальный сервер, OAuth, streamed response, tool call и завершение процесса.
   Включить WASM и ресурсы; проверить запуск без Node/Bun в PATH, но с Claude Code.
8. Подготовить матрицу сборок macOS arm64/x64 и Linux x64/arm64 по мере проверки.
   Windows пока не обещан. Для macOS учесть подпись/notarization при подготовке
   публичного распространения; кросс-компиляция не заменяет проверку на ОС.
9. Обновить README: установка, вход, выбор модели, doctor, upgrade/uninstall,
   перенос данных, отличие от официальных клиентов, лицензии и ограничения.

Не публиковать пакет/релиз и не отправлять изменения upstream автоматически:
публичное имя, аккаунт и публикация пользователем ещё не определены и не поручены.
Подготовку, локальную упаковку и проверки можно выполнять без остановок на
подтверждение обычных обратимых инженерных решений.

## Проверки и критерии готовности

Имеющиеся проверки ранее проходили:

```sh
cd /Users/corvus278/Projects/claude-codex
node verify.cjs
bun verify-transport.cjs
```

Transport test использует настоящий обработчик CCR, но **внешний ответ
подставной**. Он проверял смену 4 моделей, effort, преобразование инструментов и
Responses Lite без перезапуска сервера. Это не доказательство доступа к этим

и отмены, tool use/tool result, нескольких одновременных сессий, ошибок/лимитов,
refresh токена, атомарных настроек, сессионных overrides и обновления пакета без
потери данных. Реальные smoke tests отделить от offline tests.

Отдельно проверить содержимое `npm pack --dry-run` и реального tarball:
**никаких `.runtime`, токенов, backups, логов или конфигов пользователя**.
Опираться на явный `files` allowlist, одного `.gitignore` недостаточно.

loopback-портов и запись в глобальный npm bin. Пользователь выполнял нужные
команды из своего терминала. Не повторять бесконечно одинаковые попытки и не
запрашивать уже данное разрешение заново; при ограничении подготовить всё
локально и дать конкретную минимальную команду для внешнего терминала.

Никогда не включать содержимое существующего OAuth-файла в вывод или документы.

После переименования старый путь `~/Projects/claude-sol-router` оставлен как

уже ссылаются на новый каталог. Не удалять alias до проверки внешних ссылок.
